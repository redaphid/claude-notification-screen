# Bench log, 2026-09-02 — Stage 1 running on hardware

Everything here was verified on a real board with a webcam pointed at it, not
inferred from documentation. Destined for the vault note
`paper-cranes-medallion/esp32-badge-swarm-architecture.md` (the master context
file); the vault MCP was returning 502 when this was written.

## Stage 1 is done

A ported plasma renders on the round panel at **32 fps**, driven by feature
envelopes, with ESP-NOW up and 1.97MB PSRAM free.

- **Backlight GPIO40** on the non-touch SKU was the entire original blocker.
  `TFT_BL 2` is the touch SKU's pin.
- **`TFT_RST` is 12**, not 14. **`invert = true` confirmed.** LovyanGFX with
  in-sketch config was the right call. 40MHz SPI works.
- **The board previously suspected defective is fine.** The unit on this bench
  reports USB serial `5B5F000273` — the one recorded as "screen never lit under
  any firmware tried, possibly defective." It lights perfectly once the
  backlight pin is right. Do not RMA it, and treat that suspicion about any
  other unit as a pin question until proven otherwise.
- **Sprite byte order, proven by experiment:** LovyanGFX 16-bit sprites store
  **byte-swapped RGB565**. Raw `uint16` words written into `getBuffer()` display
  correctly only when packed swapped. This matters because the effect pipeline
  writes pixels directly into the sprite for speed.

## The power lesson, which changes how firmware must be ordered

Bringing up WiFi is the biggest current spike this board draws. On a marginal
supply it collapses the 3V3 rail and takes the **CH343 USB bridge down along
with the ESP32**. From the host this is deeply misleading: it looks exactly like
the firmware *hanging inside* `WiFi.mode()` — the last line printed before
silence — while USB re-enumerates every ~6 seconds.

What actually fixed it: **bring the radio up before the panel and its
backlight.** Every milliamp not spent on a backlight at the moment of the RF
inrush is headroom. With that ordering the badge boots reliably; with the old
ordering it failed every boot.

Also in the firmware now: CPU dropped to 80MHz across the spike, TX power
reduced, and an RTC-memory boot-attempt counter that skips the radio entirely
after three failed boots, so a badge renders locally rather than becoming a dead
disc in a stranger's hand.

Two further notes: a badge **conducting** (transmitting continuously at 30Hz)
still browns out on a weak USB supply — an argument for the 1.46 conductor
having its own power. And host-side, `cdc_acm` can wedge hard (`Errno 71`, then
`Errno 110` on every esptool reset) while the device still enumerates. No
software recovery without root: replug the cable.

## Second frozen contract

Alongside `ChorusPacket` there is now `effects/effect.h`: a
`(features, time) -> 240x240 RGB565` signature that compiles unchanged for the
badge and for a desktop harness, so effects are developed and *watched* on a
laptop with no hardware.

Three effects ported, measured by instruction count on the actual xtensa
objects: **plasma ~5.8ms, iris ~8.8ms, tunnel ~9.4ms** per frame at 240MHz,
against a 25ms budget with a ~12ms blit. The shared polar LUT lives in PSRAM —
a 115KB sprite plus a 115KB LUT plus the WiFi stack does not fit in the S3's
320KB of internal RAM.

## Design decision worth preserving: do not smooth twice

The badge does **not** smooth received features. The conductor already ships
designed attack-decay envelopes; filtering them again on the badge reintroduces
precisely the lag that shaping them was meant to remove. The only time-based
term on the badge is `presence`, which fades a badge out over ~600ms when it
stops hearing a conductor — a designed release, not a filter. A badge that walks
out of range exhales instead of freezing on its last packet.

## Conductor stream findings (Stage 2, compile-verified, not yet on hardware)

- **I2S mic pins for the 1.46**, from Waveshare's own `MIC_MSM.h` cross-checked
  against two wiki tables: **BCLK 15, WS 2, DIN 39**, standard I2S (not PDM).
  Which stereo slot the mic drives is undocumented, so the firmware listens to
  both at boot and takes whichever moves.
- Waveshare's demo targets Arduino core 3.1.1 and `ESP_I2S`, which does not
  exist in 2.0.11. Pin numbers carry over; the API calls do not.
- 1024-point window (64ms), 256-sample hop, 16kHz: big window for bass
  resolution, short hop for onset timing. **Kick-to-packet ~27ms typical.**
- **Wind:** a 2-pole 40Hz high-pass was nowhere near enough — pure gusting
  produced **53 false onsets** and drove bass to 0.67, because venue-adaptive
  normalization z-scores a noise floor up to full scale in a quiet field. Sixth
  order Butterworth helped but did not fix it. The fix was a silence gate keyed
  on spectral flux, which separates music from wind by ~100x. Wind now yields
  **0 onsets**. The Iceland-wind problem, solved before Iceland.

## Also landed

One badge binary with role chosen by holding BOOT at reset, mesh relay with hop
counting and sequence dedupe, and an ESP Web Tools flasher page with offsets
verified against the generated partition table (**bootloader at 0x0**, not the
0x1000 used on classic ESP32).

## Still open

- Two badges have never been in the same room with the radio on: relay, dedupe
  and hop counting are compile-correct and single-board tested only.
- The conductor firmware has never run on the 1.46; its mic pins are strongly
  sourced but unconfirmed.
- The web flasher has never actually flashed a board.
